## Context

The client (`src/Triviador.Client`) is a hand-written CSS + plain React app (Zustand store, no
Tailwind/CSS-in-JS, `motion` for animation). The map is a single `<svg viewBox="0 0 1200 700">`
(`GameMap.tsx`) rendering real country outlines baked at build time by
`scripts/generate-europe-paths.mjs` (d3-geo + world-atlas, dev-only deps) into
`europeGeography.ts`. Region click targets are the outline `<path>` itself with no hit-area padding
(`RegionShape.tsx`). The only responsive breakpoint is `@media (max-width: 900px)`
(`App.css`), which stacks the layout to one column but does nothing about touch-target size,
orientation, or zoom. There is no pan/zoom library in the runtime bundle today.

The 16-region map splits evenly into 8 "large" regions (value 400, legacy fallback radius 64-70)
and 8 "small" regions (value 200, radius 44-50) that the geography generator already needed manual
`LABEL_NUDGES` for (Belgium/Netherlands/Austria/Czechia) because their outlines sit too close
together. On a ~370-400px phone viewport the 1200-unit viewBox scales to roughly 0.3px/unit, putting
several small regions' tap targets well under the 44x44px guideline with no gap between borders.

## Goals / Non-Goals

**Goals:**
- Make every remaining region comfortably tappable on a phone without any client-side hit-area
  hacks that would just shift the misclick problem to overlapping invisible padding.
- Give phone players a way to zoom/pan the map for closer inspection, independent of the region-size
  fix, since even large countries benefit from zoom on a ~6" screen.
- Nudge (not force) landscape orientation, since true OS-level lock isn't available on iOS Safari
  and only works in fullscreen/PWA mode on Android Chrome.
- Keep the map-topology, game-setup-rules, and land-grab-flow specs' existing requirements true
  unmodified — none of them assume a fixed region count.

**Non-Goals:**
- Redrawing country shapes or changing the projection/viewBox size.
- A new pan-zoom npm dependency — the gesture surface needed (pinch, drag-pan, double-tap, wheel)
  is small enough to hand-roll on Pointer Events without pulling in a library plus its own bug
  surface for a feature this scoped.
- Persisting/migrating any existing game or room state that referenced a dropped region id — this
  repo has no persistence layer and no long-lived state across a deploy.
- A PWA manifest / installability — out of scope for this pass; only `viewport-fit=cover` is added
  for safe-area support.

## Decisions

### 1. Cut the 8 small regions, not just enlarge their hit area
Padding a small region's invisible hit area would make it overlap its neighbors' hit areas — on a
map where Belgium, Netherlands, Switzerland, Austria, Czechia, Denmark are already tightly packed,
that trades "misclick because too small" for "misclick because ambiguous which of two overlapping
regions you meant," which is worse. Cutting them removes the problem at the source. Chosen per the
value/radius split already present in `map.json`: every value-400 region survives, every value-200
region is cut. Kept regions: Spain, France, UK, Germany, Italy, Poland, Sweden, Ukraine.

### 2. Adjacency repair for the 8 survivors
Applying the cut to the existing adjacency lists directly would strand Sweden (its only neighbor,
Denmark, is cut) and would drop Italy to a single neighbor (France) after Switzerland/Austria are
cut. Repaired adjacency:

| Region  | New adjacentTo            |
|---------|----------------------------|
| Spain   | France                     |
| France  | Spain, UK, Germany, Italy  |
| UK      | France                     |
| Germany | France, Italy, Poland, Sweden |
| Italy   | France, Germany            |
| Poland  | Germany, Ukraine           |
| Sweden  | Germany                    |
| Ukraine | Poland                     |

Two new edges not present in the original 16-region graph: **Germany-Italy** (restores the
connectivity that used to run Italy-Switzerland-Germany and Italy-Austria-Germany) and
**Germany-Sweden** (replaces the lost Sweden-Denmark-Germany chain). Both are geographically
defensible (Alpine-adjacent, Baltic-adjacent) and keep the graph connected with no leaf regions
worse than degree 1 (UK, Spain, Sweden, Ukraine end as single-neighbor "wing" regions, same
topological role Portugal/Ireland played before).

Verified against `GameRules.MinimumBaseDistance = 2` (hop-distance, checked in
`GameEngine.BaseSelection.cs`, and already has a "relax if nothing qualifies" fallback per the
`game-setup-rules` spec): an independent set of size 4 exists in the repaired graph — e.g. {Spain,
UK, Italy, Poland} — so 4 players can still get bases at hop-distance >= 2 apart without the
relaxation ever triggering. No `GameRules` change needed.

### 3. Regenerate `europeGeography.ts`, don't hand-edit it
The file is explicitly generated by `scripts/generate-europe-paths.mjs` from `world-atlas`/
`topojson-client` data. Hand-trimming the 8 cut entries out of the generated file would work today
but silently drifts from the generator the next time someone re-runs it. The task is to update the
generator's country list and re-run it, keeping the file's "generated, do not hand-edit" contract
intact.

### 4. `MapViewport` as a wrapper component, not baked into `GameMap`
`GameMap` stays a pure `view -> <svg>` renderer (matches `client-presentation`'s "render projected
state only" spirit — no interaction state mixed into the rendering component). `MapViewport` is a
new component that wraps `<GameMap>` (or any children) in a `<div>` applying a CSS
`transform: translate() scale()` driven by pointer-event math, so `GameMap` itself needs no changes
beyond being wrapped in `App.tsx`.

Gesture handling, in order of precedence:
- **>=2 active pointers**: pinch. Track distance between the two pointers frame-to-frame; scale
  ratio = new distance / old distance, clamped to an overall `[1, 4]` scale range, zooming around
  the pinch midpoint.
- **1 active pointer and current scale > 1**: pan, clamped so the transformed map can't be dragged
  further than its own edge into view (no dragging the map away to reveal empty space).
  Implemented with a computed max-pan derived from `(scale - 1) * containerSize / 2`.
- **1 active pointer and current scale == 1**: no-op (deliberately not turned into an at-zoom-1
  pan) — this is what lets normal page scroll pass through, see decision 5.
- **Double-click / double-tap** (two `pointerup` events within ~300ms at nearly the same
  coordinate): toggle between scale 1 (reset) and a fixed zoomed-in scale (2.5), centered on the tap
  point.
- **Wheel** (desktop): zoom centered on the cursor position, same clamp range.
- A "Reset view" button appears only once `scale > 1`, so a player who pinch-zoomed and lost their
  place has a one-tap way back, rather than hunting for the exact reverse gesture.

State is held in a ref (not React state) for the pointer map and current transform, applied directly
to the DOM node's `style.transform` on every pointermove for responsiveness; only the
boolean "is zoomed" (for the reset button and `touch-action` toggle) is mirrored into React state,
so a full re-render doesn't happen on every pixel of drag.

### 5. Dynamic `touch-action` instead of a blanket `touch-action: none`
Setting `touch-action: none` unconditionally on the map wrapper would block normal page scrolling
whenever a drag starts on the map, which matters because the map sits above the roster/dock in the
single-column mobile layout. Instead `touch-action` is set to `'pan-y'` while unzoomed (`scale ===
1` and fewer than 2 active pointers) so vertical page scroll still works over the map, and switched
to `'none'` the moment a second pointer lands (mid-pinch) or the map is zoomed in (`scale > 1`, so
JS owns single-finger panning). This is set imperatively on the DOM node alongside the transform,
not via a CSS class, since it must react to pointer count within the same event that starts a
gesture.

### 6. Orientation nudge is a dismissible overlay, not a hard gate
True orientation lock (`screen.orientation.lock`) requires the Fullscreen API first and is
unsupported in iOS Safari entirely (per MDN, as of this writing) — it cannot be relied on as the
only mechanism. The primary UX is a full-screen CSS overlay (`@media (orientation: portrait) and
(max-width: 900px)`, gated additionally by the current `GameView.phase` being an active gameplay
phase, not Lobby/Landing/Results) with a "Rotate device" message and two actions: **Go fullscreen &
rotate** (calls `element.requestFullscreen()` then, in the fullscreen-change handler, attempts
`screen.orientation.lock('landscape')` in a try/catch — no-ops silently if either API is missing)
and **Continue in portrait** (dismisses for the session, via a React state flag, no persistence
needed since it's cheap to re-show next session). The overlay never blocks input to the game
underneath when dismissed, and reappears if the viewport re-enters portrait after being dismissed in
landscape (tracks live orientation via a `matchMedia('(orientation: portrait)')` listener) — so a
player who rotates back to portrait mid-game gets nudged again rather than the dismissal silently
suppressing it forever.

### 7. Touch targets and safe-area via existing breakpoint, no new one
The existing `@media (max-width: 900px)` block in `App.css` already distinguishes "phone-ish"
layout from desktop; new touch-target rules (button/option-plate/keypad min sizes bumped toward
44px, `safe-area-inset-*` padding on `.app-shell`) are added inside that same block rather than
introducing a second breakpoint, keeping the one existing responsive seam as the single source of
truth for "this is a small/touch device" styling.

## Risks / Trade-offs

- **Cutting 8 regions changes game balance/feel** (fewer territories to fight over, sparser
  adjacency graph with several degree-1 "wing" regions) → Mitigated by the independent-set check
  confirming base placement still works at the default `MinimumBaseDistance`; the land-grab and
  battle engines are already region-count-agnostic (verified via `game-setup-rules`/`land-grab-flow`
  specs), so no rule changes are required, only content. Actual play-feel is a judgment call the
  user has already made explicitly.
- **Hand-rolled pinch/pan math has edge cases a library would have already handled** (e.g. rapid
  pointer-id reuse, losing a pointer via `pointercancel` on an OS gesture interrupt) → Mitigated by
  always cleaning up on both `pointerup` and `pointercancel`, and clamping scale/pan on every frame
  so a missed event can't compound into an unrecoverable transform (worst case, "Reset view" always
  restores scale 1).
- **`screen.orientation.lock` + `requestFullscreen` is Android-Chrome-only** → Mitigated by treating
  it as a bonus, not the primary mechanism; the CSS nudge overlay works everywhere and is the
  actual fix for the majority of phone browsers (iOS Safari has no lock API at all).
- **Regenerating `europeGeography.ts` requires re-running a Node script with dev-only geo
  dependencies** (`d3-geo`, `topojson-client`, `world-atlas`) → Not a new risk (the script already
  exists and is already the documented path for changing this file); confirm `npm install` in
  `Triviador.Client` still has these as devDependencies before running it.

## Migration Plan

No data migration: no persistence layer exists, and no in-flight room state survives this deploy.
Steps are a single atomic change: update `map.json` content, re-run the geography generator, ship
the client. No rollback complexity beyond reverting the commit.

## Open Questions

None outstanding — the cut list, adjacency repair, and orientation-lock scope were confirmed with
the user before this design was written.
