## Context

The shipped map (`src/UI/Triviador.Web/Data/map.json`, `id: "europe-8"`) has 8 regions named after
real European countries, rendered client-side as real country-outline SVG paths
(`src/Triviador.Client/src/components/map/europeGeography.ts`, generated by
`src/Triviador.Client/scripts/generate-europe-paths.mjs` from `world-atlas`/`d3-geo`/
`topojson-client`, keyed by `RegionId`). `RegionShape.tsx` draws `EUROPE_GEOGRAPHY[regionId].path`
when present, falling back to the domain's circle (`centerX`/`centerY`/`radius` from
`RegionDescriptor`) otherwise. `GameMap.tsx` anchors adjacency lines, labels, and wax-seal base
markers on `EUROPE_GEOGRAPHY[...].centroidX/Y`, falling back to the server's `labelX`/`labelY`.
`MapViewport.tsx` wraps the whole `<GameMap>` in pinch/pan/zoom (scale range `[1, 4]`) and is
entirely geometry-agnostic — it transforms a `<div>`, never touches region data.

`Triviador.Domain/Map/RegionDescriptor.cs` and `MapValidator.cs` are already geography-agnostic:
the descriptor carries `NameEn`/`NameRu`/`Value`/`CenterX`/`CenterY`/`Radius`/`LabelX`/`LabelY`/
`AdjacentTo` and nothing that assumes real-world geography; the validator only checks id
uniqueness, `Value ∈ {200, 400}`, symmetric adjacency, and full connectivity. `MapRepository.cs`
deserializes `Data/map.json` into exactly those fields and fails fast on invalid content. None of
this needs to change — only the content of `Data/map.json` and the client's static geometry
dataset change.

`tools/mapgen/generate-map.mjs` is an existing, currently-unwired reference generator: a
dependency-free Node script that lays out an 18-region 6×3 grid, jitters interior/boundary lattice
vertices with a seeded PRNG (`mulberry32`), and draws each region as a closed path of four cubic
Bezier edges shared between adjoining regions (each edge computed once, cached by vertex-pair key,
so neighbors always draw an identical shared border — no gaps, no overlaps). Its current output
schema (`id`/`name`/`value`/`renderPath`/`labelX`/`labelY`/`adjacentTo`) predates the current
`MapRepository` parsing contract and does not match it (no `nameEn`/`nameRu`/`centerX`/`centerY`/
`radius`), and it only emits one file, not the two artifacts (server content + client geometry)
this change needs.

`mobile-optimization` (a separate, already-fully-implemented-in-code, not-yet-archived change) cut
the map from 16 real countries to 8 specifically because the 8 dropped countries' real-world
outlines were too small to tap reliably on a phone, and added `MapViewport.tsx`'s pinch-zoom (up to
4x) as the general phone-usability fix for the map. That pinch-zoom capability is what makes it
safe to reintroduce more, smaller regions here: a player who finds an 18-region board's cells too
small to tap accurately now has a zoom escape valve that didn't exist when the 8-region cut was
decided.

## Goals / Non-Goals

**Goals:**
- Ship an abstract, non-real-world 18-region map (`id: "abstract-18"`) with invented English and
  Russian names, organic jigsaw-piece-shaped regions, and a layout that stays fair for 2-4 player
  base selection.
- Consolidate map generation into one rewritten, dependency-free, deterministic script that emits
  both `Data/map.json` and the client's static path/centroid geometry from the same seeded vertex
  data, so the two can never drift apart the way `europeGeography.ts` could drift from `map.json`
  (a real, documented risk in the change this supersedes).
- Preserve every existing per-region visual behavior (ownership wash, eligibility ring, contested
  marker, wax seal, adjacency lines, labels) and the existing circle-fallback contract for a
  `RegionId` absent from the client geometry dataset.
- Leave `Triviador.Domain`, `Triviador.Application`, `Triviador.Infrastructure`, `MapViewport.tsx`,
  and the app-shell's responsive CSS untouched.

**Non-Goals:**
- Not re-deriving or re-tuning the responsive layout CSS (`App.css`'s `clamp()` max-width, 1440px
  breakpoint, safe-area-insets) — that was already implemented and stays as-is.
- Not touching `mobile-optimization`'s pinch/pan/zoom mechanics, orientation nudge, or touch-target
  CSS — none of it depends on which regions exist or what they're named.
- Not changing `GameRules` (round limit, `MinimumBaseDistance`, base HP, etc.) — the balance check
  below confirms the existing default works unmodified.
- Not a pixel-perfect "world-builder" fantasy map with borders, rivers, or terrain texture — the
  bar is "reads as distinct abstract lands of different shapes," matching the existing project's
  restrained, wax-seal/heraldic visual language (`HeraldicDefs.tsx`, `WaxSeal.tsx`).

## Decisions

### 1. Region count: 18, restoring CLAUDE.md's "18-territory map"

`mobile-optimization` trimmed 16 → 8 purely for touch-target safety on the old real-country
outlines, several of which (Portugal, Ireland, Belgium, Netherlands, Switzerland, Austria, Czechia,
Denmark) were genuinely tiny at phone scale. That risk doesn't transfer cleanly to a fresh abstract
layout: this change's regions are drawn on a uniform 6×3 grid (cell size below), so every region
gets a comparable footprint — there's no "the small ones are unusably tiny" problem to design
around, and `MapViewport`'s pinch-zoom (already shipped) is the general-purpose mitigation for
"still too small to comfortably tap" regardless of region count. 18 also matches the region count
CLAUDE.md has described as the target game shape since before the 8-region placeholder existed.

**Alternative considered**: keep 8 regions and only re-skin them abstractly. Rejected — the user's
explicit direction is to restore the 18-territory design; an 8-region board under-uses the adjacency
graph and land-grab pacing the rest of the domain (round limits, land-grab pick counts in
`GameRules`) was tuned against.

### 2. One rewritten generator script emits both outputs from shared vertex data

`tools/mapgen/generate-map.mjs` is rewritten (not left as reference-only) to produce, from a single
seeded vertex lattice:
- `src/UI/Triviador.Web/Data/map.json` — the schema `MapRepository` actually parses: `id`,
  `viewBox`, and per region `id`, `nameEn`, `nameRu`, `value`, `centerX`, `centerY`, `radius`,
  `labelX`, `labelY`, `adjacentTo`.
- `src/Triviador.Client/src/components/map/abstractGeography.ts` — a generated TS module (replaces
  `europeGeography.ts`) exporting `REGION_GEOMETRY: Record<string, RegionGeometry>` where
  `RegionGeometry = { path: string; centroidX: number; centroidY: number }`, keyed by the same
  region ids.

Both come from the same run so they can never disagree about which regions exist or where they
sit — the exact drift risk the real-geography version's design.md flagged (client geometry dataset
vs. server map content maintained independently) is eliminated by construction instead of merely
mitigated by a fallback.

**Alternative considered**: keep generating only `map.json` by hand and hand-author client paths
separately. Rejected — hand-authoring 18 organic shapes has no reproducibility and no update story
if the grid or seed ever changes; a script is strictly better here and one already existed as a
starting point.

### 3. Geometry parameters

- Grid: 6 columns × 3 rows = 18 regions, row-major region ids `r01`..`r18` (`regionId(row, col) =
  "r" + (row*6 + col + 1)`, zero-padded).
- `viewBox`: `0 0 1200 640` (unchanged from the reference script) — cell size `cellW ≈ 176.7`,
  `cellH ≈ 166.7` after a 70px padding margin, close enough to square that the seeded jitter
  produces natural-looking (not visibly stretched) blobs in both axes.
- Seed: `20260801` (`mulberry32`), unchanged from the reference script, kept for reproducibility —
  re-running the script against an unmodified script body always reproduces the same committed
  output byte-for-byte.
- Shape: each region is a closed 4-edge path over its grid cell's 4 lattice-vertex corners; each
  shared lattice edge is computed once (bow-perpendicular cubic Bezier, cached by vertex pair) so
  adjoining regions always draw the identical shared border — no gaps, no overlaps, no manual
  seam-fixing.
- `centerX`/`centerY` (server, used only by the circle-fallback path and never expected to trigger
  in normal operation since the client geometry always covers every generated region): the arithmetic
  mean of the cell's 4 lattice vertices.
- `radius` (server, circle-fallback only): `round(min(cellW, cellH) / 2 * 0.82)` ≈ 68, chosen to
  land in the same visual range (64-70) the previous circle-based map used, so the fallback circle
  reads at a similar scale if it's ever exercised.
- `centroidX`/`centroidY` (client, `abstractGeography.ts`): the true area-weighted polygon centroid
  (shoelace formula) of the rendered jigsaw path's 4 corners — more accurate than the vertex mean
  for placing labels/wax-seals visually centered on an irregular blob, and the value `GameMap.tsx`
  already prefers over the server's `labelX`/`labelY` whenever client geometry exists.
- `value`: middle row (row index 1, 6 regions) = 400; outer rows (row indices 0 and 2, 12 regions)
  = 200 — unchanged from the reference script, giving a 1:2 ratio of high-to-low-value territory
  consistent with the original placeholder grid's balance.
- `adjacentTo`: 4-neighbour rook adjacency (up/down/left/right grid neighbors only) — trivially
  fully connected (a grid graph is always connected), satisfying `MapValidator`'s connectivity and
  symmetry checks with no special-casing.

### 4. Balance check against `GameRules.MinimumBaseDistance`

`GameRules.MinimumBaseDistance = 2` (hop-distance) gates base selection: a candidate region within
that many hops of an already-taken base is excluded unless doing so would leave no legal choice
(`GameEngine.BaseSelection.cs`). Because the grid graph's edges are only rook-adjacent, hop-distance
between any two cells equals their Manhattan distance (`|Δrow| + |Δcol|`). Checking the four grid
corners — the most base-selection-relevant "maximally spread" candidates — confirms 4 simultaneous
bases fit comfortably above the minimum:

| Pair                  | Hop distance |
|-----------------------|--------------|
| (row0,col0)-(row0,col5)| 5           |
| (row0,col0)-(row2,col0)| 2           |
| (row0,col0)-(row2,col5)| 7           |
| (row0,col5)-(row2,col0)| 7           |
| (row0,col5)-(row2,col5)| 2           |
| (row2,col0)-(row2,col5)| 5           |

Every pair is `>= 2`, so 4-player base placement never needs the "relax minimum distance" fallback
path. No `GameRules` change is required.

### 5. Naming: invented compound names, English + Russian, no real-world references

English names reuse the existing reference script's fantasy-flavored list (`Ironreach`, `Vale of
Ash`, `Saltmarch`, `Thornhold`, `Greyfen`, `Duskmoor`, `Highgarth`, `Stonewick`, `Fenmoor`,
`Ashvale`, `Ravenhollow`, `Wolfmere`, `Emberfall`, `Sunreach`, `Thistledown`, `Blackmere`,
`Windhaven`, `Grimwood`) — already non-real-world, already fits the wax-seal/heraldic visual theme.
Russian names are newly authored, invented compound terms in the same register (e.g. `Ironreach` →
`Железный Предел`, `Vale of Ash` → `Пепельный Дол`, `Grimwood` → `Мрачный Лес`) — translated in
spirit, not transliterated, and checked against real Russian/Ukrainian place-name roots to avoid
accidental overlap (e.g. avoiding `-город`/`-градъ`/existing city names). Full 18-pair list is
authored directly in the generator script (single source of truth) rather than duplicated in this
document.

### 6. Client-side rename: `EUROPE_GEOGRAPHY` → `REGION_GEOMETRY`

`RegionShape.tsx` and `GameMap.tsx` currently import `EUROPE_GEOGRAPHY`/`RegionGeometry` from
`europeGeography.ts`. Both switch their import to `REGION_GEOMETRY`/`RegionGeometry` from the new
`abstractGeography.ts`; the lookup-by-`RegionId` and circle-fallback logic in both files is
otherwise unchanged (same `geometry ? path : circle` branch, same centroid-vs-`labelX/labelY`
fallback for markers).

### 7. Delete the real-geography pipeline entirely

Delete `src/Triviador.Client/src/components/map/europeGeography.ts` and
`src/Triviador.Client/scripts/generate-europe-paths.mjs`, and remove their-only-consumer
devDependencies (`d3-geo`, `@types/d3-geo`, `topojson-client`, `@types/topojson-client`,
`world-atlas`) from `src/Triviador.Client/package.json`, regenerating `package-lock.json` via
`npm install`. The new generator needs zero npm dependencies (same posture as the original
`tools/mapgen/generate-map.mjs`), so nothing replaces them.

### 8. Delete `realistic-europe-map-responsive-layout`, keep its shipped CSS

That change's proposal/design/specs describe the real-geography approach this change reverses; per
explicit product direction the folder is deleted outright rather than archived (archiving would
record real-geography rendering as an accepted, historical capability, which is misleading once
`abstract-map-rework` supersedes it before that capability ever reached `openspec/specs/`). Its
responsive-layout CSS in `App.css` (fluid `clamp()` max-width, 1440px breakpoint, safe-area-insets)
shipped independently of the geography question and is untouched by this change.

## Risks / Trade-offs

- **18 regions on the same viewBox as the old 8-region map means smaller average cell size** →
  mitigated by `MapViewport`'s pinch-zoom (already shipped, `MAX_SCALE = 4`) and by the uniform grid
  cell sizing (no region is disproportionately smaller than another, unlike the old 200-value
  countries which were visibly tiny next to the 400-value ones).
- **Rewriting the generator changes its output schema and adds a second output file** → contained
  entirely within `tools/mapgen/generate-map.mjs`; no other code depends on its old output shape
  (it was never wired into the build), so there's no compatibility surface to preserve.
- **Deleting `realistic-europe-map-responsive-layout` instead of archiving it** → acceptable per
  explicit product direction; the responsive-layout half of its work is preserved in `App.css`
  regardless of what happens to the change-tracking folder, so no implementation work is lost, only
  the (now-inaccurate) proposal/design narrative describing a real-geography board.

## Migration Plan

No data migration: no persistence layer exists, and no in-flight room state survives this deploy
(same precedent as the `europe-16` → `europe-8` cut). Steps are a single atomic change: rewrite the
generator, run it to produce `map.json` + `abstractGeography.ts`, update the two importing
components, delete the superseded files/deps/change folder, ship. Rollback is reverting the commit.

## Open Questions

None outstanding — region count, naming register, and the generator-consolidation approach were
settled directly in this document.
